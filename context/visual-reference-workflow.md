## Before assuming the page template — check the actual spec structure first

Not every subject's pages follow the same Visual Reference template richness. Two variants seen so far:

- **Coarse template** (Cell/Molecular Biology & Biochemistry, most subjects to date): one Interactive bullet per page, marked `*(built later — see project workflow)*`, with the implementation technology left for the building session to choose.
- **Rich template** (Ethology, confirmed by inspection before that subject's pass began): **two** Interactive bullets per page, each with the implementation technology already decided and named in the bullet itself (e.g. "(Plotly)", "(SVG/JS)", "(HTML/JS, no new library)", "(drag-and-drop, HTML/JS)", "(audio-triggered HTML/JS, no new library)") — no `(built later)` parenthetical at all, and a per-page `<!-- VIDEO: ... -->` HTML comment specifying a real, specific video to source and embed (see the new "Per-page VIDEO comments" section below). Ethology's pages had this full spec already written and committed, with zero Static/Interactive work done — a genuinely fresh start, not another undocumented-partial-work situation.

**Rule going forward: before proposing a first batch for a new subject, read at least 2-3 of its pages' full `## Visual Reference` sections** (not just grep for `built later`) to see which template variant applies, how many widgets per page, whether tech is pre-assigned, and whether per-page video comments exist — don't assume the pattern from the previous subject carries over unchanged. The Interactive-widget phase has no separate ledger — its completion state is just "does every `**Interactive**` heading still say `(built later — see project workflow)`, or does it have real `{{< iframe >}}` embeds" on each page.

## Token-conservation mode (adopted partway through Plant Anatomy, 2026-08-04)

The user explicitly asked to cut token usage on this workflow. Two adjustments were adopted and should carry forward as the new default unless a session is told otherwise:

- **Batch multiple pages per round, not one page at a time.** Once a subject's pattern is established (first page or two done normally), propose the *remaining* pages' Static-image requests together in one message rather than page-by-page. The user sources them in one or a few passes; insertion/captioning/ledger work then happens in fewer, larger tool-call sessions instead of many small ones.
- **Drop the per-page live dev-server verification** (the `curl` + `grep` placement-order and serve-status check described below) once it's proven reliable for the subject (it did, 10/10 pages, zero placement failures). Replace it with a single lightweight serve-status loop (curl each new file, print only failures) after each batch, and **one full `hugo --minify` build + reference-resolution check at the very end** of the whole Static-image pass (same check as the Interactive-widget phase's existing step 6) rather than a live-render check after every page. Still view every image with the Read tool before captioning — that step is about content accuracy, not something the token-saving adjustment touches.

Phase order was also flipped for Plant Anatomy specifically (all Interactive widgets built first, in one uninterrupted pass, *then* Static images) at the user's explicit request, to reduce context-switching overhead within a single long session. Both orders work; default to Static-first (the original order) unless a session says otherwise.

## The core workflow (steady-state loop)

1. **I propose a batch** for one page: usually all of that page's Visual Reference `Static` items (typically 4-6), each with a short description of what to look for and an exact filename to save it as.
2. **The user sources the images themselves** — searches, evaluates candidates, saves the file to the exact path/filename I specified under `static/<SECTION>PICS/`. I do not fetch or download images myself; the user does, then tells me the source (a URL, or a plain-text attribution like "public domain" / "credit in image" / a named site).
3. **I verify the files exist** (`ls`), then **view every one with the Read tool** before writing anything — never caption from the filename or the user's one-line source description alone. This step has caught real problems every batch: content that doesn't match the original spec, wrong file formats, accidental duplicates.
4. **I write an accurate caption based on what the image actually shows**, not what was originally requested. If a sourced image is broader, narrower, or adjacent to the spec (common), say so explicitly in the caption or a trailing note — never silently force a caption that overclaims what's in the picture.
5. **I insert the image inline in Key Concepts**, directly under the paragraph/subsection it illustrates — see "Placement philosophy" below, this is a deliberate, user-directed departure from the original template.
6. **I update `image-sources.md`** (the ledger) with the new row(s) before or immediately after wiring in.
7. **I verify the live render** against the local Hugo dev server (see "Verification" below) — confirm the image sits under the correct heading and returns HTTP 200, not just that the markdown looks right.
8. **I report back concisely**: what's placed, what's flagged, what's dropped, then the next batch's requests.

## Placement philosophy — inline, not bottom-of-page

**Original template had a single `## Visual Reference` section at the bottom of every page** (Interactive + Static subsections, per `handoff.md`). The user explicitly overrode this for Static content: *"there does not have to be a visual reference portion... when these concepts are introduced and explained, the image should be presented then and there, it is really a bad idea to make people scroll to the bottom."*

Applied as follows, confirmed as the standing rule for this project:

- **Static images**: placed inline in `## Key Concepts`, immediately after the sentence/paragraph they support, using ordinary markdown image syntax. The `## Visual Reference` section's `**Static**` subsection is deleted entirely once a page's images are placed — replaced with a one-line note: `*(Static images are placed inline in Key Concepts above, next to the concept each one illustrates, rather than collected here.)*`
- **Interactive widgets stay in `## Visual Reference` at the bottom** — the user explicitly confirmed this when asked ("No, rather than going inline, the widgets will be at the bottom"). Don't move them inline without asking again if a new session considers it.
- The `**Interactive**` heading gets `*(built later — see project workflow)*` appended until those widgets are actually built — see "The Interactive widget workflow" below for that phase. Once built, the parenthetical is removed and each spec bullet is followed by an `{{< iframe >}}` embed, same placement pattern as the Static heading's inline images but staying in the Visual Reference section rather than moving into Key Concepts.
- A page is "done" for this workflow once every Static item is either placed inline, explicitly dropped (see below), or intentionally left unillustrated (rare, only when nothing usable was found — say so in the leftover Visual Reference note).

## Image conventions

- **Directory**: `static/<SECTION>PICS/` — one flat directory per section, matching the site's pre-existing convention (`MCBBPICS`, `ECOLOGYPICS`, `BIOINFOPICS`, `ANATOMYPICS`). Create it once per new subject with `mkdir`.
- **Filename**: descriptive kebab-case, assigned by me when I request the image (e.g. `root-water-pathways-apoplast-symplast-transcellular.png`), so there's no back-and-forth about naming. Always give the user the exact path when requesting.
- **Markdown**: standard `![alt text](/SECTIONPICS/filename.png)` followed immediately by an italic attribution line: `*Source: <who/where> — confirm licensing basis before public deployment*` (wording varies slightly but always flags unresolved licensing unless truly confirmed open).
- **Alt text carries the real content description** — write it as a full sentence describing what the image shows structurally, since it doubles as the caption for accessibility and for anyone scanning just the markdown source.

## Licensing: default posture is "flag, don't block"

This project's standing instruction: **source anything, even with doubt — insert it, but flag clearly.** Concretely:
- `CHECK` (the default): source isn't confirmed CC/open-license/public-domain. Insert anyway, caption with "confirm licensing basis before public deployment," log in the ledger.
- `OK (likely)`: source is from a publisher with a known open-access default (Frontiers, MDPI — both confirmed CC BY 4.0 by default during this project). Still worth a final check before public deployment, but meaningfully better footing than a bare `CHECK`.
- **`CONFIRMED COPYRIGHT`** — reserve this stronger flag for images carrying an explicit, visible copyright notice in the image itself (e.g. "© Merriam-Webster, Inc." printed directly on a diagram). This is categorically different from "unconfirmed" — surface it distinctly in both the ledger and the inline caption, don't let it blend into the general `CHECK` pile. Still insert per the user's standing preference, but say plainly that it must not go on the public site without a license or replacement.
- **ResearchGate / ScienceDirect "topics" pages / Wiley / Springer chapter links are essentially never confirmed-open** by default — flag every one, even when the content match is excellent. Frontiers and MDPI are the two sources encountered so far with a genuine open-access default worth calling out positively.
- If the user explicitly overrides a flagged concern ("continue with the current images"), update the ledger to say so explicitly (e.g. *"Inserted per user decision to proceed despite the flagged concern"*) rather than quietly clearing the flag — the caution should stay visible for the eventual public-deployment pass even after the decision to proceed.

## The ledger: `image-sources.md`

One running file at the repo root (not inside `content/`, so it never gets built into the site). Table columns: `Filename | Directory | Used on page | Source | Status | Notes`. Append rows every batch, immediately — don't batch up ledger updates for later. This file is the single source of truth for the eventual "confirm all licensing before public deployment" pass across every subject, so keep it complete and current rather than reconstructing it retroactively.

## Handling real-world messiness (all of this happened at least once)

- **Mismatched file extension**: a user-saved file is sometimes a different real format than its extension claims (an AVIF or SVG saved as `.png`). The Read tool's error message names the actual detected format — confirm with `file <path>`, then `mv` to the correct extension and reference that in the markdown. Note the fix in the ledger; it's not a licensing issue, just a housekeeping one.
- **Two "different" images turning out to be the same source at different crops**: happened once (an apoplastic-only crop and a combined apoplastic+symplastic crop from the same figure). Use the more complete one for both concepts it covers, mark the redundant one `NOT INSERTED` in the ledger with a one-line explanation, don't insert both.
- **A sourced image doesn't match the original ask**: sometimes what's found is broader (e.g. a whole guard-cell metabolism map requested as a narrow "ion flux" diagram), narrower/adjacent (a generic PIN-transport diagram substituted for an unfindable Cholodny-Went-specific one), or from a different scientific domain than expected (a generalized animal/human HSF pathway figure used for a plant heat-shock concept). In every case: insert it, caption exactly what it shows, and add a short note (inline and in the ledger) about the gap between what was asked for and what's actually there. Never quietly caption it as if it were the originally-requested content.
- **User explicitly drops an item** ("no image for this, remove"): delete the spec bullet/content entirely — no residual mention, no placeholder. Confirm the removal leaves no trace when you grep the rendered page afterward.
- **A user-provided substitute is explicitly incomplete** (e.g. "substitute without the specific result shown" — a grafting-technique diagram that doesn't show the flowering outcome the text needed): still insert it if requested, but the caption must say plainly what's missing, so nobody mistakes the illustration for actually depicting the claim in the text.
- **Video, not image**: if the user provides a YouTube link for a spec item instead of a static image, embed it with Hugo's built-in shortcode `{{< youtube VIDEO_ID >}}` (already used elsewhere in this codebase — no new plumbing). Before embedding, verify the video is actually on-topic (a quick `WebFetch` on the URL for the title is enough) rather than trusting the link blindly. Log it in the ledger with `Status: N/A` and a note that it's an embed, not a hosted file.
- **A stray image with no caption arrives mid-conversation**: this has happened more than once and always turned out to be an accidental clipboard/screenshot paste, not a real instruction. If a message is only image + auto-generated coordinate-mapping metadata with zero accompanying text, treat it as noise — briefly say so and continue; don't stall the batch waiting for clarification a second time once the pattern is established.
- **The user's numbered list of sources doesn't always match the numbered list of requested images** — sometimes what actually got saved fits a different slot better than the order implies (e.g. a source titled "dormancy regulation model" turned out to match the file meant for a different spec item than the one it was listed against). Match by actual content, not by list position; note the reassignment transparently in the ledger.
- **A source URL is given but the file never actually landed on disk** — happened once in Plant Anatomy (a `nature.com` link provided for a spec item, but `ls` on the target directory showed no matching file at all, under the requested name or any other). Don't guess a substitute or silently drop the item — flag it explicitly to the user (in chat and in the ledger, `Status: HOLD`) and leave the spec item unillustrated rather than either fabricating a caption for a nonexistent file or quietly proceeding as if it were sourced.
- **A sourced image can turn out to be a genuine content duplicate of a different spec item, not just a different crop of the same source** — happened in Cell/Molecular Biology (a file sourced and named for "nucleotide structure: base+sugar+phosphate" turned out to show the same ribose-vs-deoxyribose comparison already sourced separately for a different spec item, just a different rendering). Same handling as the same-source-different-crop case: use the one that's the better/more specifically-matching fit, mark the redundant one `NOT INSERTED` in the ledger with a plain explanation, and leave the original spec item's slot explicitly unillustrated rather than force-captioning the duplicate into a role it doesn't fill.
- **AI-generated images need a distinct flag from licensing, for accuracy rather than copyright** — an AI-generated (e.g. Grok) SDS-PAGE infographic in Cell/Molecular Biology had garbled, sometimes-wrong embedded text (a mislabeled unit, misspelled words, nonsense OCR-like artifacts in places) despite being conceptually correct overall. This is not a licensing problem (`CHECK`/`OK`/`CONFIRMED COPYRIGHT` doesn't capture it) — call it out explicitly in both the caption and the ledger as an accuracy caveat ("don't treat any specific label/number in this image as authoritative"), separate from and in addition to the standard licensing flag.
- **A large SVG with no embedded `<text>` nodes cannot be verified the way a normal image can, and that's worth disclosing rather than glossing over** — the Read tool's image renderer fails outright on SVGs over ~256KB, and the usual fallback (grep/extract `<text>`/`<tspan>` content, as worked for a large-but-text-rich TCA-cycle SVG) only works if the SVG actually contains text nodes. One large Cell/Molecular Biology SVG (a detailed fluid-mosaic-model illustration) had zero `<text>` elements — purely path/circle-based art. In that situation: open it in the Browser pane (`preview_start`/`navigate` to the raw SVG file URL) and use `javascript_tool` to pull structural facts (`viewBox`, counts of `<path>`/`<circle>`/`<g>` elements) as the best available substitute for eyeballing it — the Browser pane's `screenshot` action is unreliable in this environment (see the existing note below) and converting an SVG to a raster for the Read tool isn't straightforward from a sandboxed page-JS context. Say plainly in the caption/ledger that the image could not be fully visually verified and recommend a spot-check before public deployment, rather than describing content you didn't actually confirm.
- **A whole subject can arrive from a prior, undocumented session already partially illustrated** — Plant Anatomy's own handoff prompt for the *next* subject (Cell/Molecular Biology & Biochemistry) turned out to already have ~20 images placed across 3 of its 22 pages and a handful of pre-existing, unattributed site assets logged only as "backfill" ledger rows, from work this workflow file has no record of. Before proposing a first batch for any subject, `grep -rl "PICS/" content/resources/<section>/*/_index.md` (or the section's specific `*PICS` directory name) to check for existing inline images, and cross-check against `image-sources.md` for that section — don't assume a subject starts at zero just because this file's revision history doesn't mention it.
- **Cross-referencing instead of re-sourcing near-duplicate images is a legitimate move, not just a fallback** — on Plant Anatomy's synthesis page (`Monocot-Dicot-Comparative-Anatomy`), 3 of 6 originally-specced Static items would have duplicated images already placed on three other pages covering the same organs. Proposed skipping those 3 and only sourcing the 2 genuinely novel items instead, cross-linking to the existing images from the synthesis page's text; user agreed. Worth proposing proactively whenever a page's spec list overlaps content already illustrated elsewhere in the same subject, not just when a duplicate is discovered after the fact.

## Per-page VIDEO comments: a distinct pattern from the "Video, not image" Static case

Some subjects' pages (Ethology, confirmed before its pass began) embed a `<!-- VIDEO: description — Species name — why this specific clip matters -->` HTML comment inside `## Visual Reference`, below the Static bullet list — one real, specific video the page's own spec is asking to be sourced and embedded. This is **not** the same as the existing "Video, not image" bullet under "Handling real-world messiness" above, which covers a Static *item* the user happens to substitute with a video link mid-conversation — this is a per-page, template-level request present in the committed content from the start, describing exactly what footage is needed and why (e.g. "the coordination between individuals during a hunt is the actual mechanism producing the higher per-capita capture success rate cited in text").

Handling: treat it like any other Static-phase item needing sourcing — request it from the user the same way (the comment already states what to look for, no need to re-derive a description), verify the found video is actually on-topic before embedding (a quick `WebFetch` on the URL for the title, same precedent as the existing video-handling note), then **replace the entire HTML comment** with `{{< youtube VIDEO_ID >}}` once sourced — don't leave the comment behind alongside the embed. Log it in `image-sources.md` with `Status: N/A` and a note that it's an embed, not a hosted file, matching the existing convention. Don't delete the comment before a real video is actually confirmed and embedded — it's the record of what's still outstanding, the same way an unfilled Static bullet is.

## Verification (do this every batch, not just at the end)

Don't trust that a markdown edit "looks right" — confirm the live page:

1. Make sure a Hugo dev server is running (`.claude/launch.json` has a `hugo-dev` config: `hugo server --port 1313 --disableFastRender`). Start/reuse it via the browser tool's `preview_start`. If it's died (check `curl -o /dev/null -w "%{http_code}" http://127.0.0.1:1313/`), just restart it — a stray Windows file-lock on old `public/` build output has caused this at least twice now (recurred again during Cell/Molecular Biology's Interactive-widget verification) and a restart clears it. **If `preview_start {name: "hugo-dev"}` reports success but the server still doesn't actually come up** (curl keeps failing), the underlying `hugo.exe` process may not have actually restarted — check with `tasklist //FI "IMAGENAME eq hugo.exe"` (Windows), `taskkill //PID <pid> //F` the stale one if present, then launch it directly as a Bash background process: `hugo server --port 1313 --disableFastRender > /tmp/hugo.log 2>&1 &` and re-check `curl`. **The Browser pane also has a tab cap** — if `preview_start` reports "Tab cap reached," the `Write` tool's post-write hook auto-opens a `file://` preview tab for every new widget file, and these accumulate fast across a multi-widget batch; use `tabs_close` on the stale `file://` tabs (check with `tabs_context`) before retrying `preview_start`.
2. **Use `127.0.0.1`, not `localhost`, in `curl` from this shell** — `localhost` has silently failed to resolve in this Bash/Git-Bash environment before (IPv6 vs IPv4 quirk), producing a misleading "server is down" false alarm. `127.0.0.1` worked every time.
3. Confirm placement order: `curl -s http://127.0.0.1:1313/resources/.../page/ | grep -o '<h3[^<]*<[^>]*>[^<]*\|SECTIONPICS/[a-zA-Z0-9._-]*\.\(png\|svg\)'` and eyeball that each image line falls immediately after the right heading.
4. Confirm every referenced file actually serves: loop `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:1313/SECTIONPICS/filename.png` for each — expect `200`.
5. If something was explicitly dropped, grep for its old spec text to confirm zero residual mentions.
6. The Browser pane's `screenshot` action is unreliable in this environment (frequently errors "pane not displayed, not compositing frames") — don't depend on it for verification. `curl` + `grep` against the dev server is the reliable substitute and was used for essentially all verification in this project. When a real visual check is unavoidable (e.g. confirming what an unreadable file format actually depicts), `javascript_tool` against the loaded page (e.g. forcing `img.loading = 'eager'` and reading `naturalWidth`/`complete`, or reading `svg text` node contents) is a more reliable fallback than screenshotting.

## The Interactive widget workflow (steady-state loop)

Proven end-to-end across Evolution's 11 pages (22 widgets — every page's two `**Interactive**` bullets). Unlike the Static-image phase, there's no sourcing step — this is real code, written directly, no batches or user approval needed per widget (the plan/breakdown approval already covers the whole subject).

1. **Build every widget as a standalone file under `static/`, one file per widget**, named descriptively in kebab-case matching the spec's bolded name (e.g. `hardy-weinberg-calculator.html`, `red-queen-simulator.html`). **Do not embed widgets inline in the page's markdown as a `<div>/<script>` block** — a standalone file is never run through Hugo/goldmark, so it's structurally immune to the blank-line gotcha below, which cost real debugging time in Plant Physiology. Two of Plant Physiology's four widgets were inline and had to be written blank-line-free by hand; all 22 of Evolution's widgets were standalone files and none hit that bug. Prefer standalone every time now — there's no longer a reason to embed inline.
2. **Match the established visual system in every widget**: `'Inter', system-ui, -apple-system, sans-serif`; cream page background `#fefcf5`; white rounded card (`border-radius: 24px`, `box-shadow: 0 8px 20px rgba(0,0,0,0.05)`, `padding: 1.5rem`, `max-width` 620–760px depending on content); heading color `#1a472a`; a left-border-accented `.subtitle` line (`border-left: 3px solid #2d6a4f; padding-left: 12px`) restating what the widget demonstrates; primary action buttons `background: #2d6a4f; color: #fff; border-radius: 999px`; a consistent small palette for semantic color (`#1d70a2` blue for one series/correct-adjacent, `#d9534f` red for the other series/danger, `#dcfce7`/`#166534` green and `#fee2e2`/`#991b1b` red for correct/incorrect feedback states). Copy an existing widget file as a starting template rather than reinventing the CSS each time.
3. **Use Plotly (via `<script src="https://cdn.plot.ly/plotly-3.1.0.min.js"></script>` in the widget's own `<head>`)** for anything the spec names "(Plotly)" — histograms, multi-generation trajectory plots, timelines with a continuous underlying curve. Everything else (sorters, clickable maps/diagrams, quizzes, sliders driving an SVG) is plain SVG/CSS/JS, no library, per the spec's own "(SVG/JS, no new library)" framing. **When a subject's spec bullets don't pre-tag a technology at all** (the coarse `(built later)` template — see the new section near the top of this file), use judgment from the described interaction: sliders that continuously redraw a mathematical curve (e.g. Cell/Molecular Biology's Michaelis-Menten/Lineweaver-Burk explorer, sliders for `[I]`/`K_I`/`K_I'` redrawing two live plots) are a Plotly case even without an explicit tag; discrete click/toggle/step interactions over a diagram are plain SVG/JS.
4. **Wire the widget into the page** by replacing `**Interactive** *(built later — see project workflow)*` with `**Interactive**` (drop the parenthetical) and inserting `{{< iframe src="/widget-filename.html" title="..." height="Npx" >}}` directly after the spec bullet it corresponds to, same pattern as the existing `cohesion-tension-simulator.html` precedent. Pick `height` to fit the widget's actual content (~400-500px typical) rather than reusing one constant for every widget.
5. **Verify by actually exercising the interaction, not by checking the DOM loaded** — see the dedicated gotcha section below. This step alone caught three real, shipped-looking bugs in Evolution's widgets that a "does the iframe return 200" check would have missed entirely.
6. **Confirm the full build stays clean and every reference resolves**: `hugo --minify`, then grep every page's built HTML for `src=/[a-zA-Z0-9._-]*\.html` and confirm each file exists under `static/`, and confirm no page is missing an expected iframe count (2 per page has been the norm so far — count them, don't just spot-check).

## Interactive widget gotcha: no blank lines anywhere inside an inline HTML block

Discovered across the second and third pages' widgets (Stomatal Physiology, then again in Phloem Transport — broader than first thought): **a blank line anywhere inside an inline raw-HTML block in the markdown — `<div>`, `<svg>`, `<script>`, all of it — breaks Hugo/goldmark's raw-HTML passthrough at that point**, and everything after the blank line gets reprocessed as markdown instead of passed through as raw HTML/JS.

- If the blank line is inside a `<script>`: the JS after it silently fails (straight quotes become curly quotes, a stray `<p>` appears mid-script, no console error — buttons/sliders exist but do nothing).
- If the blank line is inside markup like an `<svg>` (found this the second time, one page later): indented lines after the blank line get parsed as an **indented code block** instead — the elements vanish from the actual DOM entirely (wrapped in `<pre><code>` and HTML-escaped), so `getElementById` returns `null` for anything defined after the blank line.

Both failure modes look fine in the raw markdown and even in a casual read of the built HTML — the page builds clean, no errors anywhere. The only way to catch it is to check that specific elements exist and actually respond to interaction.

**Rule going forward: never put a blank line inside *any* inline HTML block (div/svg/script) embedded directly in a content `.md` file — from the opening tag to its matching closing tag, keep it fully blank-line-free.** Standalone widget `.html` files under `static/` are unaffected (not run through goldmark at all) — this only bites inline HTML/JS embedded directly in a page's markdown. Skip blank lines for readability inside these blocks entirely; keep them dense, or separate visual sections with a comment line instead if needed.

**Verification implication**: don't just check that a widget's container `<div>` exists in the rendered page — for every element referenced by `getElementById` inside the widget's script, confirm it round-trips (element is non-null) *and* actually exercise the JS (via `javascript_tool`: click buttons, dispatch `input` events on sliders, read back the resulting DOM state) before calling a widget done. A quick sanity check worth running preemptively on any new widget: grep the widget's markdown block for blank lines before ever loading it in a browser.

```bash
awk '/^<div id="widget-id"/{flag=1} flag && NF==0{print NR": blank line found"} flag && /^<\/script>$/{flag=0}' path/to/_index.md
```

## Interactive widget gotcha: sequential animations must reset state before replaying

Found on the fourth page's PMF animator: a button-triggered multi-step reveal (opacity 0→1 on several elements via staggered `setTimeout`s) **only animates correctly the first time**. On a second click, every element is already sitting at its final `opacity: 1` from the first run, so nothing visibly changes except the caption text — the user sees no animation at all, just flickering captions. This was caught by the user testing it directly ("the 2nd visual reference needs to function better"), not by my own verification, which had only checked that the sequence *reached* its final state once, not that it could be replayed.

**Rule going forward: any click-triggered sequential/staged animation must explicitly reset every element it touches back to its initial state at the start of the click handler**, before the `setTimeout` chain re-reveals them. Concretely: factor the "initial state" into its own `reset()` function, call it first thing inside the click listener, and only then schedule the staggered reveals. Where it helps, relabel the trigger button (e.g. "Activate" → "Replay") so it's clear repeated clicks are expected and supported.

**Verification implication**: testing a sequential-reveal widget once through to completion is not enough — click it a second time and confirm the visual state actually resets and replays, not just that the caption text changes. This is a distinct failure mode from the blank-line bug above (that one breaks silently at build time; this one only shows up at interaction time, and only on the *second* interaction).

## Interactive widget gotcha: "the iframe returns 200" proves nothing — always exercise the actual interaction

Confirmed hard during Evolution: every one of the 22 widgets returned HTTP 200 and rendered visible content on first load, and would have passed a check that stopped there. Three real, functional bugs were only caught by actually driving the interaction via `javascript_tool` and reading back the resulting DOM/state:

- **A closure bug** in the homology/analogy drag-and-drop sorter: on an incorrect drop, the code scheduled a `setTimeout` to return the chip to the tray, but referenced the outer `dragged` variable inside the callback — which had already been set to `null` by the time the timeout fired 1.6s later, so the chip silently never came back and the tray slowly emptied with repeated wrong guesses. Fix: capture the item in a local `const`/`var` at drop time, use that inside the timeout, not the outer mutable variable.
- **A dimming bug** in the founder-effect/bottleneck sampler: after correctly dimming non-sampled dots and un-dimming the sampled subset, a leftover `setTimeout` un-dimmed *every* dot a moment later, silently erasing the entire visual point of the widget (showing which individuals were and weren't sampled).
- **A missing lock** in the punctuated-equilibrium fossil-series guesser: the two guess buttons (Gradual/Punctuated) never disabled after the first click, so a user (or a careless verification pass) could click both in sequence and read the answer off the second button's feedback instead of being held to one guess.

None of these were visible from a screenshot or from confirming the container `<div>` existed — all three required actually clicking, dragging, or advancing state and reading the resulting DOM back. **Rule going forward: for every widget, script a `javascript_tool` sequence that performs the *actual* user action (not just checks presence) and asserts on the resulting state, for every distinct interactive path the widget has (correct answer, wrong answer, reset, replay), before calling it done.** Two reusable recipes worth keeping:

- **Simulating HTML5 drag-and-drop** (native `dragstart`/`dragover`/`drop`/`dragend` don't fire from a plain `.click()`): construct a real `DataTransfer` and dispatch a `DragEvent` of each type in sequence at the source and target elements —
  ```js
  function fireDnd(source, target) {
    const dt = new DataTransfer();
    source.dispatchEvent(new DragEvent('dragstart', {bubbles:true, cancelable:true, dataTransfer:dt}));
    target.dispatchEvent(new DragEvent('dragover', {bubbles:true, cancelable:true, dataTransfer:dt}));
    target.dispatchEvent(new DragEvent('drop', {bubbles:true, cancelable:true, dataTransfer:dt}));
    source.dispatchEvent(new DragEvent('dragend', {bubbles:true, cancelable:true, dataTransfer:dt}));
  }
  ```
- **Triggering a Plotly click handler**: a real click on a canvas-rendered Plotly trace is unreliable to simulate via coordinates. Instead call the chart's own event emitter directly once the plot object (`gd`) is captured from `Plotly.newPlot(...).then(gd => ...)`: `gd.emit('plotly_click', { points: [{ curveNumber: 1, pointIndex: 4 }] })` — this exercises the exact same handler a real click would, without needing pixel-accurate coordinates.
- For anything running an `await`/`setTimeout`-based sequence (staggered reveals, generation-stepped simulations), wrap the whole check in `(async () => { ... })();` as the top-level `javascript_tool` expression — bare top-level `await` is rejected by the tool with a syntax error.
- **The Browser pane's tab can be background-throttled by the browser's own timer policy, making `setTimeout`-stepped animations appear to run far slower than their coded interval** — hit repeatedly in Cell/Molecular Biology: a widget stepping every 60ms took several *seconds* per step under `javascript_tool` verification, even though the code and interval were correct. This is a property of the test tab not being the foregrounded/visible tab, not a widget bug. Don't burn many verification turns waiting out a full real-time animation under this throttling. Instead: (1) confirm the underlying state/direction/label logic is correct via short, targeted checks (e.g. switch between several discrete modes and confirm each produces the right immediate values, as done for the motor-protein walk animator's three motor types), and (2) if you do want to confirm eventual completion, accept partial progress over a bounded wait (a few seconds) as sufficient evidence the recursion is advancing correctly, rather than waiting for full completion at the coded interval.

## Interactive widget gotcha: an unescaped apostrophe inside a single-quoted JS string breaks the whole script, silently

Found in Ethology's reinforcement-schedule widget: a data object had a note string written as `'...produces a "scalloped" pattern: slow right after reinforcement, speeding up as the interval's end approaches.'` — the apostrophe in `interval's` terminates the single-quoted string early, and everything after it is parsed as bare tokens, throwing a `SyntaxError` at parse time. Because this is a **standalone** widget file (not inline HTML in markdown, so the blank-line gotcha above doesn't apply), the failure mode is different but just as silent: the whole `<script>` block fails to parse, so **nothing in it ever runs** — no buttons get wired up, no chart renders, and critically, `read_console_messages` did not surface the error in this environment. The page loads with HTTP 200, the container `<div>`/`<script>` tags are present in the DOM, and it looks completely blank with zero visible cause.

**How this was actually found**: none of the usual checks caught it (no console error surfaced, DOM structure looked fine). The fix was fetching the widget's own HTML via `fetch()` inside `javascript_tool`, regex-extracting the inline `<script>` body, and running it through `new Function(scriptSrc)` — this throws the real `SyntaxError` with a location hint (e.g. `"Unexpected identifier 's'"`), which a normal page load never surfaced.

**Rule going forward**: before trusting "the page loads, buttons should be wired," treat total silence (empty container, zero note text, zero button labels) as suspicious in its own right — don't assume it's just slow to render. If a fresh widget shows no populated content at all, run the `fetch` + `new Function()` parse-check above as a fast first diagnostic before checking anything else; it's cheaper than debugging DOM/timing issues that don't actually exist. Also worth a quick preemptive grep across a batch of new widgets for a bare `'...'s ` pattern (an apostrophe following a word inside what looks like a single-quoted string) before ever loading them in a browser — cheaper than finding it after the fact.

## Interactive widget gotcha: an undirected "reduced activity in favorable conditions" simulation needs an explicit dwell mechanic, or it produces no visible effect at all

Found in Ethology's kinesis-vs-taxis widget: the first implementation modeled kinesis as "lower turning probability + lower speed" as humidity increases, with dots otherwise doing a continuous random walk. Over hundreds of simulated steps, the population stayed essentially at its starting ~50/50 split — no visible clustering in the humid half, even though the underlying textbook claim (reduced activity in favorable conditions produces aggregation with no directed steering) is correct. The reason: a plain random walk with only a *reduced step size* at low-activity positions does not, on its own, bias the long-run occupancy distribution toward those positions — under a naive (Itô-style) discretization this requires an explicit extra drift term to show the textbook "particles pile up where diffusion is low" result, which a straightforward step-size reduction alone doesn't provide.

**The fix**: add an explicit probabilistic **pause/settle state** — with some probability proportional to local humidity, an individual stops moving entirely for several steps before resuming. This is a legitimate simplification of orthokinesis (real kinesis includes changes in overall activity level, not just turning rate), and it reliably produces visible aggregation because paused individuals are, by construction, more likely to be sampled as "currently in the humid zone" — increasing dot count from 24 to 32 and steps-per-click from 40 to 80 also helped push the effect above the visual noise floor for a group this size.

**Rule going forward**: when a widget is meant to demonstrate an emergent statistical effect (aggregation, clustering, drift) arising from a locally-undirected rule, don't assume a plausible-sounding local rule (slower movement, less turning) will actually produce the claimed emergent effect — **run the simulation via `javascript_tool` over many steps and check the aggregate statistic actually moves in the claimed direction before considering the widget done**, the same way a click-driven widget's interaction must be exercised rather than trusted from a screenshot. If the effect isn't showing up, don't just increase parameters blindly — reconsider whether the underlying mechanic (here: continuous motion vs. explicit dwell time) is capable of producing the effect at all.

## What's explicitly out of scope for this workflow

- **Public deployment / final licensing resolution** is not part of this pass. Every `CHECK`/`CONFIRMED COPYRIGHT` row in `image-sources.md` is a deliberate deferral, not an oversight — a final licensing pass across the whole ledger is a distinct future task.
- **Custom-drawn SVG diagrams for Static images were tried once and abandoned** — the first pilot image was a hand-coded SVG, and the user redirected immediately to "sourced real images, I'll find and save them" as soon as they saw a real textbook figure was available and better. Don't default back to drawing originals for a *Static* image slot unless a subject genuinely has no findable real diagram for a specific concept (rare). This does not apply to *Interactive* widgets, which are hand-written SVG/JS/Plotly by design — the two phases are different in this respect and shouldn't be conflated.
